    9. Casus: de server voor de belastingberekening in NestJS

    9.1. Samenvatting van de vereisten

    De te porteren server is een server voor de berekening van de inkomstenbelasting (PHP) (zie Inleiding tot de taal PHP7 aan de hand van voorbeelden), opgebouwd in lagen (Config / Entities / Model-DAO-Business / Controllers / Responses / Views), met een frontcontroller (main.php) die binnenkomende verzoeken — die allemaal de vorm van een URL hebben (main.php?action=...) — op basis van de actie doorstuurt naar de juiste controller. Het doel van de port was om deze MVC-architectuur ongewijzigd over te nemen in NestJS, actie voor actie en statuscode voor statuscode, zodat die compatibel blijft met de HTML/TypeScript-client die al voor de PHP-server was geschreven.

    9.2. De MVC-architectuur wordt overgenomen

    De toewijzing tussen de twee servers is eenduidig:

    • Config/config.json ↔ ConfigService;
    • Entities/*.php ↔ entities/*.entity.ts (TaxAdminData, Simulation);
    • Model/ServerDao*.php ↔ ServerDaoService (laag [DAO], Hoofdstuk 5);
    • Model/ServerBusiness.php ↔ ServerBusinessService (laag [business], regel voor regel besproken);
    • Controllers/*Controller.php (één per actie) ↔ één actiecontroller per TypeScript-klasse, dynamisch geselecteerd door een register (ActionsRegistryService);
    • Responses/*Response.php ↔ ResponseSenderService (JSON, XML) en HtmlViewRendererService (HTML);
    • Views/*.php ↔ EJS-templates (views/*.ejs), met dezelfde Bootstrap-layout.

    Opmerking: Alle acties van deze server lopen via één enkele route, http://localhost:3000/main.php; de naam van de gevraagde actie wordt altijd opgegeven als parameter van de query string, ?action=action-name — nooit in het URL-pad. Dit is een bewuste URL-opzet die afwijkt van de voorbeelden uit de vorige hoofdstukken (de acties [/a01], [/m01]... die via een padsegment worden gerouteerd) en die hier precies zo is behouden als op de oorspronkelijke PHP-server, om compatibel te blijven met de client die al is geschreven.

    9.4. De frontcontroller

    Eén enkele controller (NestJS, MainController) ontvangt alle verzoeken naar /main.php?action=...     @Controller()
export class MainController {
  constructor(
    private readonly configService: ConfigService,
    private readonly responseSender: ResponseSenderService,
    private readonly actionsRegistry: ActionsRegistryService,
  ) {}

  @All('main.php')
  async handle(@Req() request: Request, @Res() response: Response): Promise<void> {
    const action = String(request.query.action ?? '').toLowerCase();

    if (!this.actionsRegistry.has(action)) {
      // ... status 102: ongeldige actie
    }
    if (!request.session.type && action !== 'init-session') {
      // ... status 103: geen sessie actief
    }
    if (!request.session.user && action !== 'authenticate-user' && action !== 'init-session') {
      // ... status 104: niet-geauthenticeerde gebruiker
    }

    const controller = this.actionsRegistry.get(action);
    const result = await controller.execute(config, request, request.session);
    // ... de respons opbouwen en verzenden (§6.7)
  }
}

    Laten we deze code toelichten:

    • regel 1: [@Controller()] — deze decorator markeert de klasse als een controller van NestJS -- hier zonder argumenten gebruikt: er wordt geen gemeenschappelijk voorvoegsel ingesteld; de route die hieronder op de methode zelf is opgegeven, bepaalt het exacte voorvoegsel;
    • regel 3: [constructor(...)] — constructorinjectie van drie @Injectable()-providers: de configuratieservice, de service voor het verzenden van antwoorden en het register van acties -- NestJS instantieert en levert ze automatisch, zonder dat u ergens new ConfigService() hoeft te schrijven;
    • regel 9: [@All('main.php')] — @All is een routedecorator die de volgende methode koppelt aan alle HTTP-methoden (GET, POST, PUT, DELETE...) voor de opgegeven URL — hier /main.php (deze naam, overgenomen van de PHP-server, verwijst in NestJS alleen naar een URL-pad en niet naar een daadwerkelijk uitgevoerd PHP-bestand); hierdoor kan dezelfde controller zowel leesacties (GET, bijvoorbeeld init-session) als acties waarmee gegevens worden verzonden (POST, bijvoorbeeld calculate-tax) afhandelen, met één enkele gedeclareerde route;
    • regel 10: [@Req() request: Request, @Res() response: Response] — twee parameterdecorators die we al zijn tegengekomen: @Req() injecteert het volledige request-object (HTTP-methode, headers, query, body, sessie...), en @Res() injecteert het response-object van Express, waarmee u volledige controle hebt over wat wordt teruggegeven — hier noodzakelijk omdat deze controller afhankelijk van de situatie zelf de HTTP-statuscode en het antwoordformaat (JSON, XML of HTML) moet kiezen, wat een eenvoudige return -instructie niet met zoveel precisie zou toestaan;
    • regel 11: [const action = String(request.query.action ?? '').toLowerCase();] — de parameter action wordt handmatig uit request.query gelezen — omdat we hebben gekozen voor @Req() in plaats van de decorator @Query('action') uit het vorige hoofdstuk, moet de code de waarde zelf uit het request-object ophalen;
    • Regel 21: [const controller = this.actionsRegistry.get(action);] — zodra de randvoorwaarden zijn gecontroleerd, handelt MainController de actie niet zelf af: het gebruikt de naam van de actie om de bijbehorende actiecontroller te vinden (zie de volgende paragraaf) en delegeert het werk daaraan.

    Opmerking: Deze controller gebruikt @Req() en @Res() in plaats van de afzonderlijke decorators (@Query(), @Body(), enzovoort) uit het vorige hoofdstuk: hij heeft volledige toegang tot het request (methode, alle parameters) en volledige controle over het verzonden antwoord (keuze van statuscode en formaat) nodig — precies zoals main.php dat deed met de objecten Request en Response van Symfony.

    @Injectable()
export class CalculateTaxController implements ActionController {
  constructor(
    private readonly dao: ServerDaoService,
    private readonly business: ServerBusinessService,
  ) {}

  async execute(config, request, session): Promise<ActionResult> {
    // ... validatie van de geposte parameters [married, children, salary]
    // (dezelfde numerieke statuscodes als de oorspronkelijke PHP-controller)

    const taxAdminData = await this.dao.getTaxAdminData();
    const result = this.business.calculateTax(married, children, salary, taxAdminData);

    const simulations = session.simulations ?? [];
    simulations.push(Simulation.fromAttributes({ married, children, salary, ...result }));
    session.simulations = simulations;

    return { statusCode: 200, status: 300, content: { response: result }, headers: {} };
  }
}

    Laten we deze code stap voor stap bekijken:

    • regel 1: [@Injectable()] — het eerste belangrijke punt: CalculateTaxController is een gewone provider (@Injectable()), geen controller van NestJS — hij heeft noch @Controller() noch routes (@Get, @Post...); alleen MainController (hierboven besproken) wordt door de HTTP-router van NestJS herkend;
    • regel 2: [export class CalculateTaxController implements ActionController] — deze klasse implementeert de projectspecifieke interface ActionController (gedefinieerd in action-controller.interface.ts), die slechts één methode vereist: execute(...) -- dit is een projectconventie, geen mechanisme van NestJS;
    • regel 3: [constructor(...)] — constructorinjectie van twee services: DAO ([DAO]-laag, toegang tot de belastinggegevens) en bedrijfslogica ([business]-laag, zuivere berekening);
    • regel 8: [async execute(config, request, session): Promise<ActionResult>] — de methode die wordt aangeroepen door MainController.handle() (controller.execute(...), zie hierboven) -- de parameters ervan zijn geen decorators van NestJS (@Body(), @Session()...), omdat deze methode nooit rechtstreeks door de HTTP-router wordt aangeroepen: MainController geeft hem het request en de sessie die hij zelf via @Req() heeft ontvangen handmatig door;
    • regel 12: [const taxAdminData = await this.dao.getTaxAdminData();] — haalt de belastinggegevens (schijven, drempels) op die voor de berekening nodig zijn, via de [DAO]-laag die in het vorige hoofdstuk is besproken;
    • regel 19: [return { statusCode: 200, status: 300, content: { response: result }, headers: {} };] — het tweede belangrijke punt: wat execute() teruggeeft, wordt niet ongewijzigd naar de browser gestuurd — het is de projectspecifieke structuur ActionResult (statusCode, status, content, headers), die door MainController wordt verwerkt en vervolgens wordt doorgegeven aan ResponseSenderService, die het HTTP-antwoord opbouwt dat daadwerkelijk wordt verzonden (JSON, XML of HTML, afhankelijk van het sessietype — zie hieronder).

    Deze actie wordt geactiveerd door een POST-request naar http://localhost:3000/main.php?action=calculate-tax, waarbij de drie parameters „married", „children" en „salary" in de body van het request staan (en niet in de URL) — dit is in feite het eerste wat execute() controleert, nog voordat deze parameters worden gelezen.

    async execute(config: AppConfig, request: Request, session: AppSession): Promise<ActionResult> {
  const method = request.method.toLowerCase();
  const nbParams = Object.keys(request.query).length;
  if (method !== 'get' || nbParams !== 1) {
    return {
      statusCode: 400,
      status: 401,

      headers: {},

  const type = session.type;
  await new Promise<void>((resolve) => session.regenerate(() => resolve()));

    Laten we deze code toelichten:

    • regel 10: await new Promise<void>((resolve) => session.regenerate(() => resolve())); — een lastig onderdeel van deze controller: session.regenerate(callback), geleverd door express-session, is een callbackmethode en geen Promise; daarom verpakken we hem in een Promise om hem net als de rest van de code met await te kunnen afwachten; regenerate() wist de huidige sessie en kent er een gloednieuwe identifier aan toe (het equivalent van het vernietigen van de sessie in Symfony);
    • regel 11: request.session.type = type; — het tweede lastige punt: na regenerate() verwijst request.session naar een gloednieuwe sessie-instantie; de oude sessie-verwijzing, die vóór de aanroep in de parameters van **execute() is vastgelegd, is nu verweesd — daarom wordt het type opnieuw toegewezen aan **request.session in plaats van aan session; anders zou het ongemerkt verloren gaan.

    async send(
  request: Request, response: Response, config: AppConfig,
  statusCode: number, content: Record<string, unknown>,
  headers: Record<string, string>, type: 'json' | 'html' | 'xml',
): Promise<void> {
  let body: string;
  let contentType: string;
  switch (type) {
    case 'xml':
      body = js2xmlparser.parse('root', content);
      contentType = 'application/xml';
      break;
    case 'html':
      body = await this.htmlViewRenderer.render(content, request);
      contentType = 'text/html';
      break;
    case 'json':
    default:
      body = JSON.stringify(content);
      contentType = 'application/json';
      break;
  }
  headers = { ...headers, 'content-type': contentType };
  this.sendResponse(request, response, statusCode, body, headers, config);
  this.logger.write(`response=${JSON.stringify(content)}\n`);
}

private sendResponse(
  request: Request, response: Response, statusCode: number,
  content: string, headers: Record<string, string>, config: AppConfig,
): void {
  if (config.corsAllowed) {
    const origin = request.headers.origin ?? '';
    if (origin.startsWith('http://localhost') || origin.startsWith('https://localhost')) {
      headers = {
        ...headers,
        'Access-Control-Allow-Origin': origin,
        'Access-Control-Allow-Headers': 'Accept, Content-Type',
        'Access-Control-Allow-Methods': 'GET, POST',
        'Access-Control-Allow-Credentials': 'true',
      };
    }
  }
  const method = request.method.toLowerCase();
  if (method === 'options') {
    content = '';
    statusCode = 200;
  }
  Object.entries(headers).forEach(([name, value]) => response.setHeader(name, value));
  response.status(statusCode).send(content);
}

    Laten we deze code toelichten:

    • switch (type) { ... } — de drie antwoordformaten worden hier en alleen hier opgebouwd: JSON met JSON.stringify, XML met de bibliotheek js2xmlparser (die het object content omzet in een XML-document, met het element <root> als hoofdelement) en HTML door volledig te delegeren aan HtmlViewRendererService.render(...), dat hieronder nader wordt beschreven;
    • this.logger.write(response=${JSON.stringify(content)}); — ook in HTML-modus wordt de applicatie-inhoud van het antwoord (content) gelogd, nooit de volledige gegenereerde HTML-pagina — zoals HtmlResponse.php dat deed;
    • in sendResponse(...) repliceert de controle origin.startsWith('http://localhost') || origin.startsWith('https://localhost') exact het CORS-beleid van de oorspronkelijke PHP-server (ParentResponse::sendResponse): alleen localhost-oorsprongen krijgen Access-Control-Allow-*-headers, nooit een willekeurig domein;
    • if (method === 'options') { content = ''; statusCode = 200; } — bijzonder geval van de CORS-preflight: bij een OPTIONS-request zijn alleen de headers van belang; de body van het antwoord wordt leeggemaakt en de statuscode wordt afgedwongen op 200, ongeacht de gevraagde verwerking.

    Voor de modus type=html repliceert HtmlViewRendererService de logica voor het kiezen van een view van de PHP-server: elke antwoordstatus komt overeen met een view, gekozen uit een configuratietabel, met een terugval op een generieke foutpagina als geen enkele view past. Elke view is een EJS-template (views/*.ejs), een directe vertaling van de oorspronkelijke PHP-bestanden, aangestuurd door een „weergavetemplate" die door een speciale functie wordt gegenereerd — hetzelfde principe als het paar getModelForThisView(...) / PHP-view, met als extra voordeel het automatisch escapen van weergegeven waarden.

    Opmerking: Voor wie NestJS al elders is tegengekomen: deze HTML-rendering gebruikt de decorator @Render() van NestJS niet, waarmee een controllermethode aan een view-engine (EJS, Handlebars, Pug...) wordt gekoppeld -- Dit mechanisme vereist een traditionele NestJS-controller met één route per view, wat niet te combineren is met de enkele front-controller van deze server. ejs.renderFile(...) wordt daarom rechtstreeks en handmatig aangeroepen binnen HtmlViewRendererService, waarna de resulterende HTML als platte tekst wordt verzonden via @Res() (zie hierboven): een volstrekt geldig alternatief voor het renderen van views met NestJS, maar zonder deze specifieke decorator te gebruiken.

    case 350: {
      const married = request.body?.['married'];
      model.checkedYes = married === 'yes';
      model.checkedNo = married !== 'yes';
      model.children = String(request.body?.children ?? '');
      model.salary = String(request.body?.salary ?? '');
      model.success = false;
      model.error = true;
      model.errors = [String(content.response)];
      break;
    }
  }
  return model;
}

    Laten we deze code toelichten:

    • statuscodes 200 en 800 (leeg formulier, aankomst bij de view of terugkeer vanuit display-tax-calculation) — alle velden van het model worden leeggemaakt, alsof het formulier nooit is ingevuld;
    • status 300 (geslaagde berekening) — const response = content.response as Record<string, unknown>; haalt het resultaat op dat is teruggegeven door CalculateTaxController (belasting, korting, vermindering, toeslag, tarief) en bouwt de vijf zinnen op die in de succesbanner worden weergegeven; het formulier wordt opnieuw gevuld met de verzonden waarden (request.body), zodat de gebruiker zijn invoer naast het resultaat kan nalopen;
    • statussen 341 en 350 (database — of Redis — niet beschikbaar) — hetzelfde opnieuw weergeven van het verzonden formulier, maar met model.error = true en de foutmelding die de [DAO]-laag teruggeeft in model.errors;
    • optionsMenu: { ... } — het zijmenu (onderdeel van menu.ejs, zie hieronder) is toestandsonafhankelijk: het is altijd aanwezig, met dezelfde twee opties, ongeacht het resultaat van de berekening.

    De overige twee functies volgen hetzelfde principe:

    • buildSimulationsListModel(content) — de kortste van de vier: simulations: (content.response as SimulationRow[]) ?? [], aangevuld met hetzelfde zijmenu als buildTaxCalculationModel (ditmaal met „Belastingberekening" en „Sessie beëindigen");
    • buildErrorsModel(content) — bouwt de lijst met meldingen op die door de generieke "view-errors" -view worden weergegeven; behandelt een heel specifiek geval dat uit de oorspronkelijke PHP is overgenomen: else if (response !== null && typeof response === 'object') { errors = [JSON.stringify(response)]; }, voor het geval dat een successtatus zonder eigen view (zoals get-admindata/1000) toch op deze foutview terugvalt — de oorspronkelijke PHP zou het object dan weergeven via de methode __toString(); JSON.stringify is het TypeScript-equivalent;
    • buildLogoPath(request) — const root = pathname.replace(/\/[^/]*$/, ''); return ${root}/Resources/logo.jpg; : reconstrueert het pad naar het logo uit de map van de huidige URL (zonder de scriptnaam), zodat de banner correct blijft, ook als de applicatie in een submap is uitgerold — rechtstreeks overgenomen uit Views/v-banner.php.

    Laten we deze template toelichten:

    • regel 1: <%# ... %> — een EJS-commentaar, dat nooit naar de browser wordt gestuurd;
    • <%- include('partials/banner', { logo: logo }) %> — sluit een partial template in, met de variabelen die we er expliciet aan willen doorgeven (hier logo); let op: <%- %> geeft het resultaat zonder escaping weer — hier uitsluitend gebruikt om HTML in te voegen die al is opgebouwd door include(...), nooit voor door gebruikers ingevoerde gegevens;
    • <% if (model.success) { %> ... <% } %> — EJS-controleblok (<% %>, zonder streepje): JavaScript dat tijdens het renderen wordt uitgevoerd en zelf geen uitvoer produceert; hier verschijnt de sectie „resultaat" alleen in de uiteindelijke HTML als model.success waar is;
    • <%= model.tax %> — geëscapete weergave (<%= %>, met het gelijkheidsteken): dit is de vorm die wordt gebruikt voor alle gegevens die gebruikersinvoer kunnen bevatten (berekeningsresultaten, opnieuw weergegeven login, foutmeldingen) — EJS escapet speciale tekens automatisch, in tegenstelling tot de <?= ?> in de oorspronkelijke PHP, die dat niet deed.

    De andere drie views en de vijf partials (views/partials/) volgen dezelfde principes:

    • view-authentication.ejs — het inlogformulier; sluit partials/banner en partials/authentication-form in en toont vervolgens de lijst model.errors if model.error;
    • view-simulations-list.ejs — sluit partials/banner, partials/menu, en partials/simulations-list-table in;
    • view-errors.ejs — de terugvalview: partials/banner, partials/menu, gevolgd door een eenvoudige lus <% model.errors.forEach(function(error) { %><li><%= error %></li><% }) %>;
    • partials/banner.ejs — het logo en de titel „Calculate your tax" , gemeenschappelijk voor alle views behalve de authenticatieview, die ze ook bevat;
    • partials/menu.ejs — <% Object.keys(model.optionsMenu).forEach(function(text) { %><a href="<%= model.optionsMenu[text] %>"><%= text %></a><% }) %>: het zijmenu, dat volledig wordt aangestuurd door de tabel optionsMenu die in view-models.ts wordt aangemaakt — een menuoptie toevoegen vereist dus alleen een wijziging van het model, nooit van deze template;
    • partials/authentication-form.ejs — het Bootstrap-inlogformulier, met value="<%= model.login %>" om bij een mislukte poging de laatst ingevoerde login opnieuw weer te geven;
    • partials/tax-calculation-form.ejs — het berekeningsformulier; let op <%- model.checkedYes ? 'checked="checked"' : '' %>: een bewust en veilig gebruik van <%- %>, aangezien de ingevoegde string (checked="checked" of leeg) aan de serverzijde wordt bepaald en nooit uit gebruikersinvoer wordt opgebouwd;
    • partials/simulations-list-table.ejs — de simulatietabel, met één rij per item in model.simulations, met een „Verwijderen"-link naar main.php?action=delete-simulation&number=... voor elke rij.

    Opmerking: In tegenstelling tot de oorspronkelijke PHP, die bepaalde waarden zonder escaping opnieuw invoegde via <?= ?> (een reflected XSS-kwetsbaarheid, met name uit te buiten via het authenticatieformulier), gebruiken de EJS-templates in dit project consequent <%= %> voor alle door gebruikers aangeleverde gegevens (login, kinderen, salaris, foutmeldingen). De enkele keren dat <%- %> in dit project voorkomt, is dat uitsluitend om een partial in te sluiten of om een attribuut in te voegen dat aan de serverzijde uit een vaste waarde is opgebouwd — nooit gebruikersinvoer: dit gedrag is functioneel identiek aan dat van de PHP-server, zonder de kwetsbaarheid ervan over te nemen.
